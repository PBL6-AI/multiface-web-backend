# API Guide

This guide helps frontend, mobile, and QA contributors understand the currently exposed backend API.

## 1. Source of truth

Use these sources in this order:
1. Swagger UI at `/docs`
2. Controllers and DTOs in `src/modules/*`
3. This guide for contributor-focused context

Swagger is generated in `src/main.ts`, so it is the best runtime view of what the server currently exposes.

## 2. Local base URL

Default local base URL:

```text
http://localhost:3000
```

Swagger UI:

```text
http://localhost:3000/docs
```

## 3. Authentication model

The API uses bearer-token authentication for protected routes.

### Main auth endpoints

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| `POST` | `/auth/register` | No | Register a new student account |
| `POST` | `/auth/login` | No | Login with `userCode` and `password` |
| `POST` | `/auth/refresh` | No | Exchange a refresh token for a new token pair |
| `POST` | `/auth/logout` | Yes | Logout the current user and optionally revoke a refresh token |
| `GET` | `/auth/me` | Yes | Get the currently authenticated user |

### Login request shape

```json
{
  "userCode": "GV001",
  "password": "SecurePass123!"
}
```

### Login success shape

```json
{
  "success": true,
  "data": {
    "accessToken": "<jwt-access-token>",
    "refreshToken": "<jwt-refresh-token>",
    "user": {
      "id": 1,
      "fullName": "Teacher Alpha",
      "userCode": "GV001",
      "email": "teacher1@multiface.local",
      "role": "teacher"
    }
  }
}
```

### How to call protected routes

Send the access token as a bearer token:

```http
Authorization: Bearer <access-token>
```

Swagger is configured with bearer auth, so you can authorize once inside `/docs` and test protected routes there.

## 4. Roles and access expectations

Current system roles:
- `admin`
- `teacher`
- `student`

Common patterns:
- **admin**: full user management and face-registration review access
- **teacher**: class ownership and class-member management flows
- **student**: self-service auth/profile access, class join by code, face-registration submission

Role enforcement is implemented through guards and `@Roles(...)` decorators on protected endpoints.

## 5. Response conventions

### Success envelope

Most successful responses follow this shape:

```json
{
  "success": true,
  "data": {}
}
```

The shared success type is defined in `src/common/types/api-response.type.ts`.

### Error envelope

Errors are normalized by the global `HttpExceptionFilter`:

```json
{
  "statusCode": 400,
  "message": "Validation failed",
  "timestamp": "2026-04-16T10:30:00.000Z",
  "path": "/classes"
}
```

### Validation behavior

A global `ValidationPipe` is enabled with:
- `whitelist: true`
- `transform: true`
- `forbidNonWhitelisted: true`

What that means for clients:
- DTOs are validated strictly
- unknown fields can trigger `400` responses
- numeric/date-like DTO fields may be transformed when supported by the DTO definitions

## 6. Endpoint groups

### Authentication

Route prefix: `/auth`

Main scenarios:
- student self-registration
- login by `userCode`
- refresh token rotation
- logout and current-user lookup

Notes:
- `register` creates a new student account by default
- `login` uses `userCode`, **not email**
- `refresh` expects `refreshToken`

### Users

Route prefix: `/users`

| Method | Path | Role / access |
|---|---|---|
| `GET` | `/users/me` | authenticated user |
| `PATCH` | `/users/me` | authenticated user |
| `POST` | `/users` | admin only |
| `GET` | `/users` | admin only |
| `GET` | `/users/:id` | admin only |
| `PATCH` | `/users/:id` | admin only |

Notes:
- `/users/me` is for self-profile retrieval/update
- admin routes support user creation and role-aware management
- user DTOs include role, department, specialization, and avatar references

### Classes

Route prefix: `/classes`

| Method | Path | Role / access |
|---|---|---|
| `POST` | `/classes` | teacher or admin |
| `GET` | `/classes` | authenticated user |
| `GET` | `/classes/:id` | accessible class for current user |
| `PATCH` | `/classes/:id` | owner teacher or admin |
| `DELETE` | `/classes/:id` | owner teacher or admin |
| `POST` | `/classes/join` | student |
| `GET` | `/classes/:id/members` | owner teacher or admin |
| `DELETE` | `/classes/:id/members/:studentId` | owner teacher or admin |

Important payload details:
- schedule items include `dayOfWeek`, `startTime`, `endTime`, and `room`
- class code can be provided or auto-generated by the system
- join flow expects:

```json
{
  "classCode": "SE304-2026"
}
```

### Files

Route prefix: `/files`

Current exposed endpoint:

| Method | Path | Role / access | Notes |
|---|---|---|---|
| `POST` | `/files/test-upload` | authenticated user | multipart upload to S3 + file metadata persistence |

Multipart form fields:
- `file` (required)
- `category` (optional)
- `checksum` (optional)

Important note:
- this flow depends on valid S3 configuration in the environment

### Face registration

Route prefix: `/face-registration/requests`

| Method | Path | Role / access | Purpose |
|---|---|---|---|
| `POST` | `/face-registration/requests` | student | create a new request for the current student |
| `GET` | `/face-registration/requests/me/latest` | student | fetch the latest request |
| `GET` | `/face-registration/requests` | admin | list requests, optionally filtered by status |
| `GET` | `/face-registration/requests/:id` | authenticated user with access | get a request by id |
| `POST` | `/face-registration/requests/:id/images` | student | upload one face image to a request |
| `PATCH` | `/face-registration/requests/:id/review` | admin | approve or reject a request |

Multipart form fields for image upload:
- `file` (required)
- `pose` (required): `front`, `left`, `right`, `up`, `down`
- `checksum` (optional)
- `captureSource` (optional)
- `capturedAt` (optional, ISO datetime)
- `qualityScore` (optional, number from `0` to `1`)

Review payload example:

```json
{
  "status": "approved"
}
```

Rejected review example:

```json
{
  "status": "rejected",
  "rejectionReason": "Left pose is blurry, please retake all 5 images."
}
```

## 7. Practical notes for frontend and QA

### Use `userCode` for login
Do not build login flows around email/password only. The backend login DTO expects `userCode` + `password`.

### Treat Swagger as the live contract
If a markdown example and Swagger differ, prefer Swagger.

### Expect role-specific behavior
The same route group can behave differently depending on whether the caller is an admin, teacher, or student.

### Upload flows are not pure JSON
`/files/test-upload` and `/face-registration/requests/:id/images` use `multipart/form-data`.

### File-related testing requires S3 config
Without valid AWS credentials and bucket configuration, upload scenarios will fail even if the API server is running.

## 8. Suggested QA smoke flows

1. Login with a seeded user
2. Call `/auth/me`
3. For a student:
   - join a class by code
   - create a face-registration request
4. For an admin:
   - list users
   - list face-registration requests
   - review one request
5. If AWS config is available:
   - upload a file through `/files/test-upload`
   - upload face images to a registration request
